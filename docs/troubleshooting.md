# 按症状排障

从失败的那一层查起。每次只修改一个因素，保留对应日志与操作时间。

| 观察到的现象 | 先检查 | 能推动诊断的操作 |
| --- | --- | --- |
| VPS 本机 `curl --proxy` 失败 | Tinyproxy 是否运行、监听是否为回环、CONNECT 443 是否允许 | `systemctl status tinyproxy`、`ss -lntp`，看实际配置的日志 |
| VPS 本机成功，本地失败 | SSH 是否保持运行、本地端口是否被占用、VPS 是否允许 TCP 转发 | 查看 SSH 错误；必要时临时加 `-v`，避免公开完整调试日志 |
| 代理返回的 IP 与 FRP 入口不同 | VPS 多出口、NAT、代理上游是否改变出口 | 在 VPS 核对路由和代理配置；不能只看 VPS 管理页面上的 IP |
| Mac 宿主机成功，Docker 里失败 | 容器实际访问哪个代理地址、共享网络、服务名、隧道监听 | 按 Docker 附录在代理容器及 DST 所在网络分别测试 |
| FRP 代理注册失败 | token、名称重复、远端端口占用、`allowPorts` | 查看 frpc/frps 日志，先运行 `verify`；不要替换已有认证方案 |
| 手动直连失败 | DST 是否监听实际端口，FRP 是否使用 UDP，云安全组与系统防火墙 | VPS 与家中两端抓包，按方向定位丢包环节 |
| 手动直连快，大厅加入仍异常 | 实际游戏进程的代理变量、大厅登记时的代理日志、公开端口是否一致 | 先重启两个进程并确认 Klei CONNECT，再关联大厅加入的 UDP 流量 |
| 修改 `server.ini` 后端口没变化 | 启动参数 `-port`、镜像启动脚本是否重写文件、挂载是否指向另一个目录 | 以游戏启动日志里的 `ServerPort` 为准 |
| 地面正常、洞穴异常 | Caves 端口、代理变量、FRP 转发、分片互联是否都正常 | 入洞前后核对 10998 的持续双向 UDP，查两个世界的日志 |
| 洞穴日志持续“连接 Master 失败” | 内部分片地址、`master_port`、`cluster_key` | 分开的容器不能互用 `127.0.0.1`；按原部署网络修复内部通信 |
| 大厅 Ping 显示 `???` | 公布入口、UDP 可达性及大厅探测对应流量 | 它是线索，不能据此单独断言中继或 FRP 是否生效 |
| 延迟突然升高，但 UDP 仍持续经过 VPS | 玩家到 VPS、VPS 到家中线路、家庭上行、CPU/内存 | 将网络问题与游戏模拟负载分开；代理不能修复 VPS 绕路 |
| 重启后失效 | SSH 隧道有没有自启、容器变量是否保留、游戏是否先于代理启动 | 恢复代理与 FRP 后再启动两个游戏进程，重做大厅与切换验收 |

## 两个常见误判

**“curl 已经显示 VPS IP，所以大厅也一定正确。”** curl 只能证明这个检测请求走了代理。需要继续检查 DST 的环境、Klei 请求日志和真实游戏流量。

**“地面成功，所以整个服务器都成功。”** 去洞穴涉及另一个游戏进程和玩家端口。地面与洞穴互联、玩家到洞穴的连接，是两项不同检查。

## 提交问题时提供什么

使用 [test-record.md](test-record.md) 记录系统、DST/FRP 版本、容器方式、端口、失败步骤、日志时间和抓包观察。日志公开前删除 token、密码、真实 IP、玩家标识等无关信息；不要直接上传完整抓包。
